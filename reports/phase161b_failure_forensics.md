# Phase 161B - Failure Forensics

Date: 2026-06-05

Scope: forensic analysis only. No Atlas code was modified. No new benchmarks were run. This report uses Phase 157A, Phase 158/158A, Phase 160, Phase 161, and Phase 161A outputs plus the completed Phase 161A raw measurement artifact.

## Final Verdict

**Atlas improved but audit became stricter.**

Confidence level: **medium**.

The trust-score collapse is not clean evidence that Atlas got worse. Phase 161A changed the measurement surface: it doubled the sample count, used a broader prompt set, applied stricter expected-anchor checks, and penalized honest `ok=false target_not_resolved` Kubernetes Impact outputs as WRONG. At the same time, the audit exposed a real live-route problem: Phase 158/161 guardrails did not consistently apply to production Build and Investigation outputs, especially concept leakage such as EMA/Trading Systems.

Short version: Atlas did improve on some safety semantics, especially unsupported-language graph health and Impact target-not-found honesty. But it did not become broadly more correct, and several claimed guardrails were not integrated across the live output routes.

## Executive Findings

- The comparison is **not apples-to-apples**. Same repos and same scoring weights, but not the same prompts, sample size, classifier behavior, or handling of honest unknown/refusal outputs.
- Phase 157A was a 150-sample audit; Phase 161A was a 300-sample live re-measurement with stricter anchor expectations.
- Phase 158A estimated improvement from representative checks and static code-path review; it did not run the full 300-sample live matrix.
- Phase 161 measured a 15-scenario labeled battery and reported 0% misleading/wrong on that battery; Phase 161A tested a much broader live corpus.
- The biggest real issue is **integration**, not proof that the core algorithms got worse: Phase 158/161 guardrails exist on paper but did not prevent 35 unsafe live outputs.
- The largest audit issue is that 11 Kubernetes Impact outputs were classified WRONG even though Atlas returned `ok=false, status=target_not_resolved`, exactly the honest behavior Phase 158/161 promised.

## Metric Definition Differences

### Build Correct

- 157A definition: count only Build Plans classified CORRECT out of 50. PARTIALLY_CORRECT did not count as Correct, even when directionally useful.
- 161A definition: count only Build Plans classified CORRECT out of 100. MOSTLY_CORRECT and PARTIAL stayed separate.
- Inputs: 157A used 50 prompts across the same 8 repos; 161A used 100 prompts with broader feature and diagnostic requests.
- Criteria: 161A expected stronger task-specific anchors; it classified several outputs as MISLEADING when they selected a plausible concept but missed the exact subsystem.
- Apples-to-apples: **mostly no**. Same strict CORRECT concept, but different prompt set and stricter anchor matching.

### Investigation Correct

- 157A definition: count only Investigations classified CORRECT out of 50. Thin or noisy root-cause hypotheses were PARTIAL or MISLEADING.
- 161A definition: count only Investigations classified CORRECT out of 100. The runner penalized weak root-cause grounding, generic fallback, and concept leakage.
- Inputs: 161A doubled the sample count and included more synthetic broken-feature prompts without stack traces.
- Criteria: 161A was stricter about source-backed causality; plausible file lists without proof rarely reached MOSTLY_CORRECT.
- Apples-to-apples: **partly**. Both measure root-cause usefulness, but 161A used broader prompts and stronger evidence demands.

### Impact Correct

- 157A definition: count Impact outputs classified CORRECT out of 50. Resolved target plus expected blast-radius files could score CORRECT.
- 161A definition: count Impact outputs classified CORRECT out of 100. The classifier required stronger semantic anchor coverage and classified target-not-resolved Kubernetes outputs as WRONG.
- Inputs: 161A included 12 Kubernetes Impact prompts against Go targets that Atlas does not graph.
- Criteria: 161A treated honest `ok=false target_not_resolved` as failed output. That is inconsistent with Phase 158/161 safety requirements.
- Apples-to-apples: **no**. The 161A Impact rubric conflated lack of language support with wrong/fake impact behavior even when Atlas refused honestly.

### Trust Score

- 157A definition: weighted average over 150 samples: CORRECT=1.0, MOSTLY=0.8, PARTIAL=0.45, MISLEADING=0.1, WRONG=0.
- 161A definition: same weights over 300 samples, with `PARTIAL` equivalent to 157A `PARTIALLY_CORRECT`.
- Inputs: same repo names, different prompts and sample counts.
- Criteria: 161A added stricter failure tags and expected-anchor matching; it also made a fake-success counting error by using a top-level runner `ok` field instead of nested Atlas `result.ok`.
- Apples-to-apples: **directional only**. It is fair to say Atlas still is not trusted; it is not fair to say the exact -7.6 score delta proves product regression.
